# R3.0C CP1 — Contract Foundation (NON-PRODUCTION)

This document records the **deployment-location amendment** to the R3.0C architecture (`~/Claude/r3.0c-planning/r3.0c-architecture.md`, "v3"). It is governance/contract documentation, not a feature announcement.

## Status (read this first)

- **CP1 is a NON-PRODUCTION contract foundation.** It defines machine-readable reason codes, input/eligibility
  contracts, a credibility-metadata contract, and a comparison export envelope — and nothing else.
- **No algorithms are implemented.** No corner detection, lap-time computation, distance normalization,
  telemetry interpolation, corner pairing, or reference-lap selection exists here. There is no comparison result.
- **No runtime consumer.** The contracts live in `contracts/r3.0c/`, OUTSIDE `renderer/js/`. They are required by
  no production module, import nothing from `renderer/js/`, and are not wired into the UI, the Feature Registry,
  persistence, or any service.
- **The presence of these contracts is NOT a feature activation.** The Comparisons surface remains a deferred
  R3.0A panel; the `case_comparison` / `reference_lap` / `corner_delta` Feature IDs remain `deferred` with no
  renderer adapter. Nothing in this milestone makes lap comparison available to a user.

## Why the contracts live outside `renderer/js/`

Architecture v3 was authored on baseline `9e9ff99`, **before** R3-GATE0 merged. The current trusted baseline
`d59be8d…` ships `scripts/check-r3-0c-guard.js` as a **required** step (G) of the `trusted-verification` CI gate.
That guard correctly blocks any R3.0C production module under `renderer/js/` (by filename and by added-line
symbol scan) — exactly the `renderer/js/reference-lap.js`, `corner-delta.js`, `case-comparison.js` paths the
architecture names.

Per the governance ruling for CP1:

- CP1 **does not modify, disable, or circumvent** `check-r3-0c-guard.js`. The guard is unchanged and keeps passing.
- CP1 **adds no R3.0C production module** under `renderer/js/`.
- The contracts are therefore placed in a dedicated non-production location, `contracts/r3.0c/`, which the guard
  does not (and should not) scan. This is **not** a naming trick to evade a regex — it is an honest reflection of
  the fact that these artifacts are non-production contracts with no runtime consumer.

**Architecture v3 semantics are unchanged.** Only the *deployment location* of the eventual production code is
deferred. The reason codes, the five mandatory lap authorities, the lap-distance-only normalized-position
authority, the `delta = comparison − reference` convention, the service-owned credibility model, and the separate
bounded comparison export are all carried forward verbatim from v3 into these contracts.

## Future production integration (separate, authorized checkpoint)

Wiring R3.0C into `renderer/js/` (real segmentation, normalization, delta, pairing, reference selection, view
model, UI) requires a **separate, explicitly authorized checkpoint** — e.g. *R3.0C CP2 — Authorized Production
Integration*. Only that checkpoint may propose amending `check-r3-0c-guard.js` from a blanket prohibition into an
**explicit authorized file/capability allowlist** (with algorithm / UI / Feature-Registry activation still
blocked). That amendment must not be performed in CP1.

## Contract surface (`contracts/r3.0c/`)

| Module | Responsibility (contract only) |
| --- | --- |
| `reason-codes.js` | Frozen, unique, machine-readable reason codes + stable i18n explanation keys + a fail-closed blocked-result factory (a blocked result never carries a numeric payload). |
| `credibility-contract.js` | The credibility-metadata contract the domain/service MUST supply (ladder + provenance + confidence enums, required fields); validates only — derives no credibility. Synthetic never masquerades as real. |
| `valid-lap-contract.js` | The five mandatory lap authorities (lap identity / completeness / timing validity / track identity / sample continuity) + a fail-closed structural gate. No lap detection, no completeness computation. |
| `normalized-position-contract.js` | The normalized track-position INPUT contract: lap-distance authority ONLY, target range `[0,1)`, compatibility check. Defines eligibility + rejection reasons; implements no normalization. |
| `comparison-eligibility-contract.js` | The comparison SCOPE (same Analysis Case only; no cross-case / cross-session / inferred track match), the single `delta = comparison − reference` convention, and a composite fail-closed eligibility evaluator that yields NO comparison result. |
| `comparison-export-contract.js` | The separate, opt-in comparison export envelope with the fixed identity `racing-analyzer/comparison-export` (distinct from the case-export schemas), an envelope constructor, and a fail-closed validator that forbids raw/oversized arrays by construction. |
| `index.js` | Aggregate re-export. No runtime consumer. |

## Fixed contract semantics (carried from architecture v3)

- **Scope:** comparison is bounded to a single Analysis Case; cross-case and cross-session are unsupported in CP1;
  track identity is never inferred from case titles, filenames, or channel names.
- **Delta sign:** `delta = comparison − reference`, single convention, no alternate. The UI may never swap operands.
- **Valid lap:** five authorities required; any missing/unknown/incompatible → `eligible:false` + a machine-readable
  reason code, and no value/result is produced.
- **Normalized position:** lap-distance authority only; anything else → blocked.
- **Export identity:** `racing-analyzer/comparison-export`, deliberately distinct from the R3.0B / R2.3 case export
  (which carry no `racing-analyzer/*` string identity — they use `bundleSchemaVersion`).
- **Credibility:** owned by the domain/service layer; the contract validates the supplied metadata and never lets a
  UI/consumer derive credibility. Every conclusion carries credibility / provenance / confidence / limitations /
  blocked reasons.
- **Fail-closed, always:** unsupported / unknown / missing / incompatible states return a stable reason code with a
  human-readable explanation hook (an i18n key), never a fabricated value and never an empty-shell success.

## Reason code extensions

The directive's mandated 16 codes are defined verbatim. Three **scope / metric extensions** enforce semantics the
mandated set did not name explicitly:

- `CROSS_CASE_COMPARISON_UNSUPPORTED` — reference and comparison are not in the same Analysis Case (introduced at C1).
- `CROSS_SESSION_COMPARISON_UNSUPPORTED` — reference and comparison are not in the same session (introduced at C1).
- `METRIC_REQUIRED_CHANNEL_UNAVAILABLE` — the metric is in the supported allowlist but the raw channel(s) it
  requires are absent from the lap evidence (introduced at C2_LAP_AUTHORITY). Only that metric is blocked.

Sixteen **C3 normalized-distance extensions** name distinct refusal modes the production
normalized-distance service may emit. They exist because `MISSING_NORMALIZED_DISTANCE_AUTHORITY` /
`INCOMPATIBLE_NORMALIZATION` alone cannot describe WHY a normalization was refused (vs missing or
incompatible). Each names a single, distinct, observable property of the raw distance series that
prevented canonical normalization. The contract layer lists them; the production service emits them
from a closed allowlist (`R3_0C_NormalizedPositionContract.C3_NORMALIZE_REASON_CODES`); the
contract-foundation test cross-checks the allowlist against `REASON_CODES`. Introduced at
`C3_NORMALIZED_DISTANCE`:

- `NORMALIZED_DISTANCE_EMPTY_INPUT` — distances/times arrays absent, mismatched length, or empty.
- `NORMALIZED_DISTANCE_SINGLE_SAMPLE` — exactly one sample; a normalized axis cannot be derived from one point.
- `NORMALIZED_DISTANCE_NUMERIC_INVALID` — distance / time values contain NaN, Infinity, or non-finite numbers.
- `NORMALIZED_DISTANCE_UNSUPPORTED_UNIT` — distance unit not in `ACCEPTED_DISTANCE_UNITS`.
- `NORMALIZED_DISTANCE_UNKNOWN_DIRECTION` — direction not in `ACCEPTED_DIRECTIONS`.
- `NORMALIZED_DISTANCE_INCONSISTENT_DIRECTION` — direction claim and observed series disagree.
- `NORMALIZED_DISTANCE_NON_MONOTONIC` — series violates the requested monotonicity policy in a non-wrap region.
- `NORMALIZED_DISTANCE_INVALID_WRAP` — wrap-semantics token unsupported, or the series fails the wrap rule.
- `NORMALIZED_DISTANCE_MULTIPLE_WRAPS` — more than one lap wrap observed in a single-lap input.
- `NORMALIZED_DISTANCE_INSUFFICIENT_SAMPLES` — sample count below `policy.minimumSamples`.
- `NORMALIZED_DISTANCE_INSUFFICIENT_COVERAGE` — observed coverage below `policy.coverage`.
- `NORMALIZED_DISTANCE_GAP_TOO_LARGE` — largest normalized-distance gap exceeds `policy.normalizedMaxGap`.
- `NORMALIZED_DISTANCE_TIME_GAP_TOO_LARGE` — largest time gap exceeds `policy.timeGapSeconds`.
- `NORMALIZED_DISTANCE_EXTRAPOLATION_REQUIRED` — a requested normalized position falls outside the observed range.
- `NORMALIZED_DISTANCE_IDENTITY_MISMATCH` — identity quadruple missing / inconsistent between two compared requests.
- `NORMALIZED_DISTANCE_AUTHORITY_FORGED` — distance-authority descriptor carries a non `channel_source_declared`
  authority status; the service refuses a caller-forged authoritative flag.

All extensions are stable, unique, machine-readable, and frozen alongside the mandated codes.

## What CP1 explicitly does NOT do

corner detection · lap-time computation · distance normalization · telemetry interpolation · corner pairing ·
reference-lap selection · UI · persistence migration · recommendation / causation / driver blame · theoretical best ·
exact apex · official corner identity · any runtime wiring · any guard / CI / Feature-Registry / frozen change.
